## Concerns for the controller

1. **Out-of-plan interface mapping (mission overrides, no silent gaps):** the plan's `JobRunner { start/cancel/output }` + `RegisteredJob` shape and 4-tool surface were superseded by the task contract (`runJob`/`status`/`list`, actions `run|status|list`). Consequently there is **no `cancel` action and no `cyber_job_output` tool**: cancel semantics exist only as the timeout-kill path (`interrupted`/`outcome-unknown`), and no artifact files are written — `artifact_path` stays `null`, normalized rows live as evidence, NOT raw artifact files. The plan's raw-artifact retention and process-group kill (`setpgid`/`kill(-pgid)`) are the two visible gaps: Bun's spawn API exposes no pgid hook, so SIGKILL hits the direct child only (argv-only spawning means no shell wrapper tree, but a scanner that itself spawns grandchildren could survive a timeout kill). Documented in the runner header; if the operator wants them, they belong to a later task, not silently.
2. **`addJob` argv cap interplay:** the evidence store checks `Job argv` at 256 entries, but nuclei can legally produce 514 argv elements (256 `-u` pairs). The runner records a 250-entry head + synthetic marker (`<264 more argv entries not recorded>`) instead of failing the launch — the full argv lives in the returned `JobResult`; the store keeps a bounded, secret-checked record. If a reviewer prefers refusal-to-launch above some limit, it is a one-line change in `recordedArgv`.
3. **Stderr (and unfixed stdout remainder) are deliberately transient:** failures surface a 4000-char stderr excerpt to the caller (tool clips to 16 KiB), and no raw payload is persisted anywhere — the audit trail holds counters + truncated flags only. This exceeds "no raw output in events" (raw output is not in the store either), which matches the secret-discipline constraint better than the plan's artifact-file design, but it means post-mortem analysis of a failed run depends on re-running the job, not on stored raw text.
4. **Bun spawn PATH mechanics:** Bun 1.4.3 resolves bare names using the PATH in the spawn-`env` snapshot, NOT `process.env` mutations made after Bun's own startup (verified). The runner therefore passes `env: { ...process.env }` — spawn-time snapshot — so tests' late PATH injection works and child adapters still inherit the operator's env. Residual caveat: if a call site mutates `process.env.PATH` and then expects an old snapshot, it must snapshot itself; the runner documents this in-code.
5. **`lookupJob` looks back only 50 rows** (evidence `listJobs` hard-caps its LIMIT at 50), so `status <jobId>` for a job older than the 50 most recent resolves `unknown job id` even though the row exists. Acceptable for this task (tool text states the window); a `SELECT … WHERE jobId = ?` accessor in the evidence store would be the clean fix later.
6. **Ordering of the interrupted path:** state transition happens BEFORE row persistence, so a mid-row secret refusal (a Normalized payload that trips the store's secret heuristics) leaves a terminal-state row plus already-persisted rows and propagates the canonical refusal verbatim to the caller — partially completed evidence is kept, nothing is dropped silent, and the job never stays `running`.
7. **Fixture stubs rely on `bun` resolvable in the child's PATH** (`#!/usr/bin/env bun`); the test harness prepends the stub dir to the real PATH, which contains `bun`. If CI ever strips PATH, stubs fail — they are env-relative by design, no absolute interpreter paths baked in.
