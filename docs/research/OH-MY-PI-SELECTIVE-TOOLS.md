# Selective tool ideas from oh-my-pi

Research date: 2026-10-21. Upstream checked: [can1357/oh-my-pi](https://github.com/can1357/oh-my-pi), branch `main`. This is a selective design reference for the stock Pi 1.3 cyber package, not a proposal to adopt the OMP fork or mirror its tool surface. OMP documentation and interfaces evolve; pin and recheck before implementation.

## Baseline: tools already in Pi 1.3

This project pins `@earendil-works/pi-coding-agent` 1.3.0 in `package.json`. Pi's default tools are `read`, `bash`, `edit`, and `write`; `grep`, `find`, and `ls` are also built in but off by default, and can be enabled through tool selection. These provide file access, shell execution, exact edits/writes, content search, glob file discovery, and listing. Therefore do not create cyber-package substitutes for these generic operations. Set a deliberate Pi tool allowlist/profile instead. Pi's extension API can register additional tools; adding one runs inside Pi with the operating-system user's permissions.

Sources: [Pi v1.3.0 README](https://github.com/earendil-works/pi/blob/v1.3.0/packages/coding-agent/README.md), [tool registry at v1.3.0](https://github.com/earendil-works/pi/blob/v1.3.0/packages/coding-agent/src/core/tools/index.ts), [Pi v1.3.0 extension guide](https://github.com/earendil-works/pi/blob/v1.3.0/packages/coding-agent/docs/extensions.md), [project package manifest](../../package.json).

## What to carry forward

The most useful OMP idea is not its large collection of tools. It is a purpose-built structural code-search/rewrite path with pattern metavariables, diagnostics, limits, preview, and a distinct apply step. For a cyber-focused Pi package, structural **search** has an immediate case, with staged editing available for authorized remediation: search for sinks, unsafe deserialization, command construction, authorization checks, or crypto APIs across syntax rather than plain text. Results remain leads for human/agent review. A parse tree proves only that the parser recognized syntax; a successful AST rewrite can still change behavior, break types, violate invariants, or introduce a vulnerability. Run the project's real parser/compiler/linter/tests and review the diff after any code mutation.

Do not describe ast-grep as proving semantic correctness, finding every vulnerability, or validating runtime behavior. Report unsupported languages, parse failures, skipped files, and truncation. Preserve path, line/column, matched syntax, query, tool/version, and raw output as provenance when findings are created.

## Small proposed cyber default

Keep Pi's `read`, `bash`, `edit`, and `write`; enable its built-in `grep`, `find`, and `ls` for workspace discovery. Add focused cyber capabilities through the foundation's selected interfaces: Obscura for browser/research retrieval, `pi-subagents` for specialist parallel work, the planned checkpoint/evidence layer, and a typed scanner job runner. These requested capabilities should remain available through their chosen integrations without cloning OMP's browser, research, task, or checkpoint implementations. Add `ast_grep` as a read-only source-review capability and `ast_edit` as an opt-in structural rewrite with preview, stale-snapshot/hash checks, explicit apply, diff capture, and subsequent syntax/compiler validation. Keep LSP, external long-term memory, and other IDE-scale features out of the baseline unless the first milestone identifies a concrete need.

This is a selective integration recommendation: retain the requested capabilities while borrowing OMP's narrow interface and interaction patterns where they improve the chosen components. This source review does not validate OMP or its contributed extensions. Our implementation and verification are documented separately in the project README.

## Current upstream inventory (for completeness)

Checked against upstream `main` on 2026-10-21. These names describe OMP's registry and documentation surfaces; they are not all active in every session, nor are they a recommendation to import them. The registry marks some factories `createIf`/`create`, so availability depends on configuration or runtime support. Tool docs describe behavior, while actual session composition also depends on settings, tool selection, loaded plugins/extensions, and hidden-tool opt-in.

**Core registered tools** (`BuiltinToolName` / `BUILTIN_TOOLS`): `read`, `security_scan`, `bash`, `edit`, `ast_grep`, `ast_edit`, `ask`, `debug`, `eval`, `github`, `glob`, `grep`, `lsp`, `checkpoint`, `rewind`, `context_notes`, `new_context`, `task`, `hub`, `todo`, `web_search`, `write`, `memory_edit`, `retain`, `recall`, `reflect`, `learn`, `manage_skill`.

**Hidden tools** (separate registry; opt-in or enabled by runtime need): `think`, `yield`, `goal`.

**Documented tool pages** in `docs/tools/`: `ask`, `ast-edit`, `ast-grep`, `bash`, `browser`, `checkpoint`, `computer`, `context-notes`, `debug`, `edit`, `eval`, `generate_image`, `github`, `glob`, `grep`, `hub`, `learn`, `lsp`, `manage_skill`, `memory_edit`, `new-context`, `read`, `recall`, `reflect`, `retain`, `rewind`, `security_scan`, `task`, `todo`, `tts`, `web_search`, `write`. Treat this as a docs catalog, not a second authoritative registry: it includes pages not present in `BUILTIN_TOOLS` (for example `computer`, `generate_image`, `tts`) and filenames that differ from registered names. The registry and tool docs are the authoritative pair for determining whether a name is core and how its interface works.

**Extension and plugin surface:** OMP extensions can add model-callable tools plus commands, events, shortcuts, flags, renderers, providers, and session/UI integrations. Separately discoverable custom-tool modules add model-callable tools. Plugin packages may bundle extensions and sibling `tools/`, `commands/`, `skills/`, `hooks/`, `rules/`, `prompts/`, and MCP configuration; Gemini-style extension manifests can contribute MCP servers/tools/context. These are open-ended contributed capabilities, not a finite built-in name list. The upstream example set demonstrates patterns rather than a complete extension catalog: lifecycle/safety guards (`permission-gate`, `protected-paths`, `confirm-destructive`, `dirty-repo-guard`), custom tools/UI (`todo`, `hello`, `question`, `subagent`, `custom-compaction`), and dependency/file-trigger examples (`chalk-logger`, `with-deps`, `file-trigger`).
