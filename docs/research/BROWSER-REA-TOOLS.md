# Browser and REA research for a lean Pi harness

**Research date:** 2026-10-21. **Scope:** documentation/source research only. No REA readiness or setup command, install, browser launch, or target analysis was run. “Verified” below means checked against linked upstream documentation, not exercised locally.

## Recommendation

Treat the Pi extension, REA, and Obscura as separate pieces with explicit roles. Pi’s MCP registration starts REA; the installed `reverse-engineer-anything` skill supplies workflow instructions, but does not itself register an MCP server or install any analysis engine. REA’s bundled skill and MCP catalog are versioned with its package, and the available MCP tool list—not the skill text alone—determines what the active server can do. Pin the package, refresh the matching bundled skill through REA’s setup workflow when implementation is authorized, and confirm the Pi profile path first. The skill file requested for this research is the local version 37; it is instruction content only.

For web behavior, Obscura is available as a candidate lightweight, standalone Apple Silicon browser. Its upstream README advertises `obscura-aarch64-macos.tar.gz`, rendering included in the ordinary archive, and no Chrome/Node runtime dependency. It is a Rust browser with V8 and its own evolving DOM/CSS/network implementation. “CDP compatible” means a documented subset of protocol domains, not Chromium implementation parity. The README itself calls out long-tail CSS, some Web APIs, media, compositor effects, and font rasterization as potential differences. Obscura claims and its benchmarks are upstream claims; they have not been validated here. [Obscura README](https://github.com/h4ckf0r0day/obscura)

Use Obscura MCP for straightforward, serialized inspect-and-act work (navigate, snapshot, click/fill/type, evaluate, requests, console, screenshot/PDF, close). Use a CDP client when the experiment needs explicit target/context/page identity, low-level network interception/events, request/response bodies, or screencast. Obscura documents target creation/closure, browser contexts, Page, Runtime, DOM, Network, Fetch, Storage, Input, and IO methods. CDP affords finer control and observability, while MCP is a simpler agent-facing interface. Both execute page code and make real network requests. Obscura MCP has a current-page model and `browser_close` resets browser state; serialize its use or dedicate one server/process per experiment. For CDP, create a unique browser context and target/page per experiment, record those IDs, and do not let two investigators drive the same target. A context is a logical separation boundary, not proof of OS-level sandboxing.

For REA browser work, distinguish **passive capture** of a selected already-running browser page from **active browser scenarios**. Passive REA observation attaches to a caller-supplied loopback CDP endpoint and selected page; it does not navigate, click, evaluate, or capture prior network traffic. Active `capture_browser_scenario` launches a caller-selected installed Chrome-family executable with a temporary profile, performs a declarative action list, and captures selected final DOM/accessibility/screenshot/storage/network evidence. It does not install the browser or start the target fixture. The scenario contract explicitly says navigations follow the requested destination and ordinary page requests; it has no separate origin allowlist or request-interception layer. Its actions therefore should only target a known, authorized fixture or site. REA docs do **not** establish that Obscura is a supported/tested browser executable for this scenario path; Obscura’s own Playwright/CDP compatibility does not prove that pairing. [REA browser scenario contract](https://github.com/morluto/rea/blob/main/docs/browser-scenario-contract.md), [REA browser observation](https://github.com/morluto/rea/blob/main/docs/browser-observation.md)

For a lean reproducible harness, use a fresh owned process/profile per independent scenario, explicit browser/version/hash and target origin, fixed viewport/locale/timezone/storage seed, a named ready condition, and a bounded action sequence. Retain URL, DOM/accessibility, selected screenshots, console, and network metadata/content only as needed. Save complete REA Evidence (Evidence IDs plus exported bundle) with the target/browser identity, profile/commitment, scenario, and limits. Do not share a mutable page across sessions. If one MCP endpoint must be shared, put a single queue/lease owner in front of browser mutations; `step_id` alone does not prevent cross-session page races.

## Browser fidelity and security evidence limits

Obscura should be treated as a fast independent browser implementation for controlled behavioral exploration and scraping, not as an oracle for Safari, Chrome, Firefox, or a production victim environment. A DOM snapshot proves what this engine exposed for that run, not that another engine enforces the same policy. In particular, do not turn a single run into a security conclusion about CSP, CORS, SameSite/partitioned cookies, service workers, redirects, mixed content, TLS, site isolation, storage partitioning, permissions, or tracking prevention. CSP is integrated with Fetch and HTML processing; CORS, credentials, cookies, and redirects are interconnected browser algorithms, not just header parsing. WebKit’s privacy policy/ITP is separate browser behavior, so a generic engine does not model Safari’s policy merely because it renders the page. [W3C CSP3](https://www.w3.org/TR/CSP3/), [WHATWG Fetch](https://fetch.spec.whatwg.org/), [WebKit Tracking Prevention](https://webkit.org/tracking-prevention/)

Before making a policy/enforcement claim, choose the real engine/version that is in scope, build a minimal controlled fixture for each feature and edge case, and compare with an independent current browser plus relevant [Web Platform Tests](https://github.com/web-platform-tests/wpt). For CSP include response-header and meta delivery, inline/script/worker/resource directives and report-only; for CORS include preflight, credentials, redirect chains, and exposed headers; for cookies include SameSite, Secure, third-party context and storage partitioning; also test service worker control and redirects. Record network events and request/response facts, but distinguish browser-observed events from server logs and expected protocol semantics. Use WebKit/Safari for Safari-specific claims. No Obscura WPT suite or feature-level pass result was run for this research; the upstream repo links a separate benchmark suite, which is not itself a local conformance result.

The Obscura project has security controls worth preserving in deployment: loopback-only MCP/CDP by default, optional tokens for MCP HTTP and CDP, refusal of unauthenticated non-loopback binds, request-origin protections, bounds, and SSRF/private-network restrictions (with a deliberate override for local fixtures). Keep browser control endpoints on loopback, use a token if network-bound, do not reuse a personal profile, and use engagement-specific test accounts and keep their authenticated state out of the documentation browser. Its “stealth” switches alter fingerprinting and block trackers; leave them off for compatibility/security conformance experiments because they intentionally change behavior. [Obscura release notes](https://github.com/h4ckf0r0day/obscura/releases), [Obscura README: CDP and MCP](https://github.com/h4ckf0r0day/obscura)

## Pi and REA integration boundaries

REA’s Pi integration is a user-level `type: "stdio"` registration under `mcpServers.rea` in the effective Pi agent directory, normally `~/.pi/agent/mcp.json`, with the bundled skill under `~/.agents/skills`. `PI_CODING_AGENT_DIR` changes that directory: unset/empty uses default; `~`/`~/` expand; absolute paths and file URLs select a directory; relative paths remain relative to the invoking working directory. Relative overrides make it important to run Pi and the setup command from the same directory. The JSON file must be strict JSON. This research did not inspect or alter the local Pi config. [REA client configuration](https://github.com/morluto/rea/blob/main/docs/client-configuration.md)

The local skill is not proof that `rea` is installed, the MCP registration exists, or providers are ready. REA is a CLI/MCP server; engines and auxiliary tools are separate bring-your-own dependencies unless a specific setup path says otherwise. Android JADX needs a caller-supplied `jadx-headless-mcp` JAR plus a full JDK; REA does not install them. Binwalk/Unblob are caller-supplied and the REA firmware lane is verified on Linux x64. Current web-capture documentation distinguishes HAR, native mitmproxy, SAZ, and qlog format paths. Native mitmproxy decoding requires the documented mitmdump 12.2.3 profile on Linux; this adapter is unavailable on Mac. Several derived views accept HAR only; that is a view limitation, not a blanket absence of capture-format support. [REA installation](https://github.com/morluto/rea/blob/main/docs/installation.md), [Android guide](https://github.com/morluto/rea/blob/main/docs/android-analysis.md), [firmware guide](https://github.com/morluto/rea/blob/main/docs/firmware-analysis.md), [web capture guide](https://github.com/morluto/rea/blob/main/docs/web-network-captures.md)

### Native Apple Silicon default

For a lean native REA harness on Apple Silicon, the evidence-supported default deep-analysis route is **REA + Ghidra 12.1.4 + a full native arm64 JDK 21**, with REA’s headless provider. This recommendation is now supported by specific upstream evidence rather than the general availability of a Ghidra Mac build: REA’s installation guide records an end-to-end macOS 15.6 arm64 run against Ghidra 12.1.4, Apple clang 17 and bison 2.3; it says the resulting arm64 `ghidra_opt` passes the provider’s native-decompiler check and decompiles an arm64 Mach-O through REA. The guide also documents a source-owned `verify:ghidra` lane for host-native Mach-O on macOS. This is an upstream verification result, not a check of this Mac or all target formats. [REA installation: Ghidra macOS arm64](https://github.com/morluto/rea/blob/main/docs/installation.md), [REA test matrix](https://github.com/morluto/rea/blob/main/docs/testing.md)

The build detail matters: Ghidra 12.1.4’s Darwin make defaults to x86_64, so the arm64 path may require compiling the native decompiler with Apple’s existing toolchain using the documented `ARCH_TYPE="-arch arm64" OSDIR=mac_arm_64` overrides. The Ghidra app and full JDK must be native arm64; an x86_64 JDK under Rosetta can select the wrong native decompiler. REA issue #2785 reports that `rea-agents` 6.4.0’s doctor returned healthy with a Rosetta JDK even though analysis failed; the same case succeeded with an arm64 JDK. Treat doctor/readiness as prerequisite evidence only, then require a small real analysis on the exact package and host before relying on the provider. [REA issue #2785](https://github.com/morluto/rea/issues/2785)

This resolves the earlier docs conflict for current `main`: the detailed installation guide and merged Mac-provider work describe macOS support, while `provider-evaluation.md` still says macOS is not admitted and appears stale relative to that work. Do not project current-main support backward onto every published package. The task’s source says the local skill is version 37, but that is not the npm package version and does not establish which MCP tool catalog is running. At implementation, pin one exact `rea-agents` package version, obtain its bundled workflow skill from that same release, and inspect the active server’s tool/capability catalog. If staying on a published release, use release-tagged docs and real host verification for that release; do not mix a main-branch skill with an older server. [Provider evaluation](https://github.com/morluto/rea/blob/main/docs/provider-evaluation.md), [REA releases](https://github.com/morluto/rea/releases), [REA client configuration](https://github.com/morluto/rea/blob/main/docs/client-configuration.md)

Ghidra is the default here because the current upstream has a concrete native Apple Silicon REA path and it avoids a required commercial license. Hopper is a reasonable lower-friction alternative if a supported installation is already available, but it is commercial and its REA startup requires a completed first-run demo/license choice. IDA also has a documented macOS arm64 route, but requires its own license and a separately configured upstream IDA MCP with an admitted profile. Neither should be installed or enabled just to widen the tool list before a target calls for it. [REA Hopper setup](https://github.com/morluto/rea/blob/main/docs/installation.md), [REA IDA provider](https://github.com/morluto/rea/blob/main/docs/ida-provider.md)

## Versioned skill, Evidence export, and exclusive ownership

Keep the Pi MCP registration and REA instructions on one release snapshot: exact CLI/npm version, matching setup-bundled `reverse-engineer-anything` skill, and live `tools/list`/REA capability catalog. The skill version label (currently 37 in the local requested file) is an instruction snapshot identifier, not a provider release number. It cannot prove tools exist. When setup work begins, preview the Pi destination under the effective `PI_CODING_AGENT_DIR`, then make the client registration and skill pair agree on the pinned release. If an already-running server’s tool schemas differ from the skill, follow the server’s advertised schemas and refresh both from one version before relying on newer contracts. [REA setup and client configuration](https://github.com/morluto/rea/blob/main/docs/client-configuration.md), [REA MCP contracts](https://github.com/morluto/rea/blob/main/docs/mcp-contracts.md)

Use REA’s canonical Evidence records as the bridge between browser, package, and native findings. Each record carries target identity/digest, operation, provider/profile identity, locations, observations, inferences, limitations and unknowns. Keep browser scenario Evidence and native analysis Evidence as separate source records; correlate only through explicit identity (for example, matching SHA-256 or a supported static/runtime reconciliation), not a hand-written blended narrative. For offline transfer, export a complete Evidence bundle with `export_evidence_bundle` before closing the connection. The current MCP contract says an exported bundle can be imported before referencing its records; use that operation only when the pinned server advertises it, since tool surfaces vary by package. The CLI `evidence-import` validates a saved bundle and `evidence-export` canonicalizes it; separate CLI calls otherwise consume full saved records and do not share an MCP connection’s ledger. Keep original Evidence IDs/provenance, target/provider/profile identity, and file digests intact; do not flatten the bundle into a summary or screenshot. Obscura MCP replies are not REA Evidence by themselves: retain the raw capture and a sidecar with tool version/hash, browser mode, target URL, context/page IDs and capture time, then add an adapter only if it can create a valid REA Evidence record under the pinned schema. [REA MCP Evidence contracts](https://github.com/morluto/rea/blob/main/docs/mcp-contracts.md), [REA CLI Evidence import/export](https://github.com/morluto/rea/blob/main/docs/cli.md), [REA browser scenario contract](https://github.com/morluto/rea/blob/main/docs/browser-scenario-contract.md)

Enforce one mutable owner per browser target and one exclusive owner per native REA target/provider session. Obscura MCP’s current page should have one serialized controller; for parallel work use separate processes/profiles or CDP-created contexts and pages with explicit IDs. For native REA work, one target is bound to one deep-analysis provider; do not let two agents open or annotate the same live provider session concurrently. Even where database annotations affect only an ephemeral analysis project, their ordering changes what later queries see. Give offense and defense workers separate browser profiles, endpoints, REA connections, and working directories; share immutable exported Evidence as the handoff. Keep session owner, target digest, provider version/profile, and browser target/context IDs in the report. `close_binary` clears that connection’s retained Evidence, so export before closing. [REA provider binding](https://github.com/morluto/rea/blob/main/docs/provider-evaluation.md), [REA Evidence retention](https://github.com/morluto/rea/blob/main/docs/mcp-contracts.md), [Obscura CDP API](https://github.com/h4ckf0r0day/obscura)

## Distinct red-team and blue-team work

The same REA specialist can support both workstreams while keeping tasks and records distinct. In an authorized lab, the **red-team task** is to probe one scoped application build or fixture, use Obscura for controlled browser behavior, and use REA/Frida for targeted static or runtime hypothesis testing; report reproducible observations and exploit preconditions. The **blue-team task** is to inspect the corresponding build/configuration, validate expected browser policy in the actual target engine (Safari/WebKit when Safari is in scope), correlate telemetry and captures, then recommend and verify a mitigation. Neither side should share live browser state, session cookies, CDP endpoint, or mutable REA session. The specialist’s shared role is to provide artifact-identified static facts and reusable, sanitized Evidence; the role-specific analyst decides which experiments to run and records its own scenario Evidence. This separation reduces accidental state bleed and keeps observed behavior, inferred risk, and mitigation validation distinct.

REA Evidence is tied to an MCP connection’s retained evidence ledger. Keep source hashes, provider/profile/version, coverage and limitations with each claim. Export the bundle before closing the native session if the evidence must persist; closing clears session records. Retained evidence from another connection is not implicitly visible in the current one. For browser scenarios, export evidence at the end of the owning session and record browser target/context IDs alongside it. [REA MCP contracts](https://github.com/morluto/rea/blob/main/docs/mcp-contracts.md)

## Source boundary and open questions

Primary sources checked: the requested [Obscura project](https://github.com/h4ckf0r0day/obscura), [REA upstream](https://github.com/morluto/rea) docs and issue/release records, the local REA skill, Apple/LLVM/vendor documentation, W3C/WHATWG standards, WebKit’s tracking-prevention documentation, and WPT. Browser releases and REA `main` are moving targets. Before implementation, pin the exact Obscura artifact/version/hash and REA package/skill pair, and use real-browser conformance checks for any security-policy claim. No target was supplied for this research, so no target was selected or opened.
