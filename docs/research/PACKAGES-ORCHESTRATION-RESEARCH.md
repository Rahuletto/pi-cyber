# Pi worker and orchestration package review

**Review date:** 2026-10-21. **Scope:** source and package-catalog review only. No package was installed, executed, or tested on macOS. Three candidates were reviewed: `pi-subagents`, `@companion-ai/feynman`, and `@kontextmind/kxm`. “Source-reviewed” means the current Pi catalog entry and linked upstream docs/manifests were inspected; it does not establish code safety, Apple Silicon runtime compatibility, model quality, or operational behavior. Current versions below are Pi catalog release values, not recommendations to float on latest.

## Recommendation

Start from Pi’s supported `pi-subagents` extension for specialist workers and keep orchestration inside the existing Pi process. It already supplies foreground and background child Pi sessions, agent discovery, role-specific tool lists, model overrides, task workflows, and run controls. Add only a few project-owned, narrowly defined worker profiles for the cyber modes. A custom worker engine would duplicate lifecycle and result-handoff machinery before there is evidence it is needed.

Do not install Feynman just to obtain parallel workers: it depends on `pi-subagents`, but also bundles a research-focused extension and additional web/document/research packages. Reuse Feynman’s research patterns or selected prompt/skill files if useful; its workflows and agent roles are academic-research oriented. Defer KXM unless there is a concrete requirement for durable coordination across different harnesses, authenticated peers, or webhook-driven multi-stage jobs. KXM adds a hub, a separate CLI/Runtime and project state beyond a lean single-Pi harness.

## `pi-subagents`: reuse the worker runtime, tailor the roles

The Pi catalog identifies version 0.79.2, published October 20, 2026. Its documented install makes the extension available to stock Pi. Foreground children stream in the parent conversation; background children run in a detached runner and can be inspected, steered, waited on, or stopped later. The parent model still chooses whether to delegate, and current activation behavior can expose a small loader before the full tool schema. There is no implicit auto-review simply because the extension was installed. The catalog notes that the default `maxSubagentSpawnsPerRun` is 64 cumulative children, separate from active concurrency; set a much lower cap for this harness.

Agents are Markdown files with YAML frontmatter and a system prompt. The documented fields cover role name/description, tools, model, thinking level and other per-agent behavior; user or project definitions can override built-ins. `pi-subagents` can discover definitions from the Pi project agent directory or a package’s `pi.subagents.agents` / `pi-subagents.agents` manifest field. This is the direct path to a compact cyber role set: for example, separate read-only source/intel review, defense triage, and authorized web-assessment profiles, with distinct allowed tools and explicit evidence output requirements. These capability lists reduce what a child can call through Pi; they are not macOS process sandboxes. Children share the local host’s authority unless a separate launcher or OS boundary is configured.

The extension already offers scout/researcher/evidence-auditor/worker/reviewer/oracle patterns. Its researcher and evidence-auditor profiles need a web-access tool in the child, so do not assume package installation makes external research available. Each child is another model/tool run, with normal provider credentials and usage/cost implications; model choices can be overridden per agent. Local Pi sessions and the Node-based detached runner are aligned with a native Mac Pi/Node setup in concept, but this review did not verify a native Apple Silicon build or actual process permissions.

Use the extension’s built-in parallel support as an execution substrate, but preserve the project’s own task contract and evidence model above it. A worker should receive a bounded question, authorized mode, allowed sources/tools, relevant scope, and a requested result shape; its findings should return with source paths/URLs and uncertainty for coordinator review. Do not treat several model responses as independent validation when they share the same underlying evidence or provider. If a role needs a web tool, install and load only the chosen web-access package in the child runtime; avoid turning the default child into a broad tool mirror.

## Feynman: useful research pattern, but its CLI owns the full stack

The Pi catalog gives Feynman 0.5.51, published October 19, and its current upstream `package.json` confirms Node `>=22.22.0`. The package declares an extension, prompts, skills, themes and `.feynman/agents`; the latter uses a `subagents` manifest key that Pi’s ordinary package-resource list does not describe. Pi’s standard package docs explain that packages load resources declared in their manifests and that packages have separate module roots. Feynman’s own [package-stack documentation](https://feynman.is/docs/reference/package-stack/) explains the supported composition: its CLI launches Pi with `PI_CODING_AGENT_DIR=~/.feynman/agent` and lists Feynman plus core packages in that directory’s settings. This includes `pi-subagents` for child sessions, `pi-web-access`, `pi-docparser`, `pi-btw`, and AlphaXiv support.

The current Feynman 0.5.51 source manifest pins `pi-subagents` 0.79.1, `pi-web-access` 0.42.0, `pi-docparser` 4.0.0, and `pi-btw` 0.8.0. Thus Feynman’s dependency on the worker engine is one patch release behind the current Pi catalog 0.79.2. That dependency being present does not by itself prove that plain `pi install npm:@companion-ai/feynman` will load the dependency’s extension: Pi loads declared extension paths, and the `subagents` agent field is interpreted by the `pi-subagents` extension. The documented Feynman CLI settings are the evidence for the complete runtime; exact resource activation in a different Pi agent directory requires inspection and verification. The source manifest and docs also do not by themselves prove which exact resources the released CLI loaded at runtime. Treat that as a release-specific compatibility check, not a promise.

Feynman’s `/deepresearch` pattern—planned parallel research followed by source/citation checks—and its researcher/verifier/reviewer/writer roles are transferable. The core software, however, targets literature, paper, and ML research; the web and document parsers add interfaces the cyber harness may not need. Its docs state macOS and Linux support and its npm manifest sets the Node floor, making it a plausible native-Mac reference, not evidence of this Apple Silicon setup’s compatibility. The package includes PostHog telemetry; before using it on sensitive assessment material, inspect the current opt-out and payload policy in the exact release. A skills-only route in its docs is for Codex and OpenCode, not a substitute Pi subagent runtime.

## KXM: persistent multi-harness plane, not a drop-in child-agent package

KXM’s Pi catalog entry is version 0.7.183. Its README describes a local hub for authenticated durable messages and webhook workflows plus a local Runtime for workflow runs. Project YAML, SQLite records, project tokens, route checks, and run receipts provide useful design references for resumable work and provenance. The Pi manifest itself only loads its client extension and skills: using KXM means the separate `kxm` CLI, hub/Runtime lifecycle, project initialization and authenticated Pi workers, not just adding one package. It supports mixed harnesses; KXM checks whether a harness owns the selected model and documents routes it will refuse, so it can be less flexible than a single-Pi local worker pool. Each worker also uses its own harness credentials/provider path; model calls still incur the provider’s normal cost.

There is a source/version discrepancy to resolve before any future evaluation: the catalog says 0.7.183, while the linked upstream repository’s current `main` `package.json` says 0.7.1 and Node `^22.19.0 || >=24.0.0`. This report relies on the catalog for published version/manifest metadata and the README’s stated architecture, not on an assumption that `main` equals the released tarball. KXM claims local-first operation; no arm64 Mac run or cross-harness flow was tested. Its hub/workflow features are worthwhile future references if this project needs durable inter-harness jobs, but otherwise duplicate more than the worker pool requires.

## Decision for the lean cyber harness

Reuse the existing supported Pi child-session engine before creating custom orchestration. Keep one worker package, set a deliberately low per-run spawn limit, and add only a small number of cyber-specific agents with explicit tool/resource grants. Let the existing coordinator own offense/defense mode state, scope, browser identity and evidence handoff; specialist agents should return bounded reports rather than making independent global workflow decisions. If later requirements demand durable cross-harness coordination, evaluate KXM’s hub and credential/routing model as a separate layer. If research needs deeper parallel literature-style synthesis, borrow Feynman’s planning and verification pattern, and selectively validate individual resources instead of adopting its complete CLI stack.
