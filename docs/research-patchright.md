# Patchright: what it patches, and where it fits in a modern bot-detection bypass stack

*Research note, October 2026. Factual claims are cited inline; items marked **[inference]** are our synthesis, and items marked **[internal]** are observations from our own stack, not external sources.*

Patchright ([Kaliiiiiiiiii-Vinyzu/patchright](https://github.com/Kaliiiiiiiiii-Vinyzu/patchright)) is a patched, drop-in replacement for Playwright (Python/Node/.NET), Chromium-only — Firefox and WebKit are unsupported. Crucially, its patches live in the driver/client code, not in a browser binary: the repo ships a Playwright tree whose TypeScript driver/client is rewritten (via `ts-morph` AST transforms of `patchright_driver_patch.ts` into ~30 driver patch modules plus a `patchright.patch` file with ~5,900 inserted lines per the [pim97 comparison analysis](https://raw.githubusercontent.com/pim97/anti-detect-browser-tools-tech-comparison/master/patchright.md)). This runtime-level nature is central to both its power and its limits.

## 1. The vanilla Playwright/CDP leak catalog

Everything below is shipped-by-default behavior of stock Playwright (or stock Puppeteer/ChromeDriver analogues) that real anti-bot systems check for.

### 1.1 The Runtime.enable leak (the big one)

All CDP drivers call `Runtime.enable` on every frame to receive execution-context events for `page.evaluate()`. When the Runtime domain is enabled, Chromium's V8 inspector intercepts `console.*` calls and serializes arguments into a remote-object preview — which *reads* those objects, on the main thread, in page-visible ways ([Rebrowser, "How to fix Runtime.Enable CDP detection"](https://rebrowser.net/blog/how-to-fix-runtime-enable-cdp-detection-of-puppeteer-playwright-and-other-automation-libraries); [DataDome, "How New Headless Chrome & the CDP Signal Are Impacting Bot Detection"](https://datadome.co/threat-research/how-new-headless-chrome-the-cdp-signal-are-impacting-bot-detection/)). The canonical probe (DataDome 2024):

```js
var e = new Error();
Object.defineProperty(e, 'stack', { get() { detected = true; } });
console.log(e); // getter fires only when the CDP inspector serializes the argument
```

Used by "all major anti-bot software such as Cloudflare, DataDome" ([rebrowser-patches README](https://github.com/rebrowser/rebrowser-patches)). Variants and history:

- **May 2025 V8 patch war.** Two V8 commits (May 7 and 9, 2025) stopped user-defined getters from firing during console previews (`getErrorProperty` / ScriptId guard in `value-mirror.cc`), killing the Error-stack getter *at the engine level* ([Castle analysis via crawlex blog](https://blog.crawlex.net/blog/detecting-cdp-runtime-enable); [svebaa, "How V8 Leaks Your Headless Browser's Identity"](https://svebaa.github.io/personal/blog/cdp-fingerprinting/)).
- **Prototype-chain Proxy variant (still live as of early 2026).** `Object.create(proxy)` passed to `console.groupEnd()` walks the prototype chain during serialization and trips the Proxy trap — synchronous, deterministic ([palimpsest issue #3](https://github.com/copyleftdev/palimpsest/issues/3), March 2026; [svebaa 2026](https://svebaa.github.io/personal/blog/cdp-fingerprinting/)). This is why patching only the Error-getter probe was insufficient.
- **Headless variant**: headless Chrome returns `Notification.permission === 'denied'` while `navigator.permissions.query({name:'notifications'})` returns `'prompt'` — an impossible contradiction in a real browser ([palimpsest #3](https://github.com/copyleftdev/palimpsest/issues/3)).
- Test surfaces: [rebrowser-bot-detector](https://raw.githubusercontent.com/rebrowser/rebrowser-bot-detector/main/index.js) (`runtimeEnableLeak`, `exposeFunctionLeak`, `sourceUrlLeak`), [brotector](https://kaliiiiiiiiii.github.io/brotector/), [deviceandbrowserinfo.com/are_you_a_bot](https://deviceandbrowserinfo.com/are_you_a_bot).

### 1.2 Launch-flag and navigator signals

- **`navigator.webdriver`** — set by Chrome when launched with `--enable-automation` (documented behavior; [crawlex headless roundup](https://blog.crawlex.net/blog/headless-chrome-detection)); vanilla Playwright sends that flag, and Sannysoft-style suites test it directly.
- **Default Playwright args as a "stealth driver" tell** — shipped args like `--disable-popup-blocking`, `--disable-component-update`, `--disable-default-apps`, `--disable-extensions` diverge from any real user browser; Patchright explicitly removes these ([Patchright README](https://github.com/Kaliiiiiiiiii-Vinyzu/patchright)).
- **Old-headless UA tokens** — `HeadlessChrome/…` in the UA string and `sec-ch-ua` client hints; Chromium headless historically shipped no `Accept-Language` and empty `navigator.languages`/plugins ([crawlex](https://blog.crawlex.net/blog/headless-chrome-detection); [CloakBrowser table](https://github.com/CloakHQ/cloakbrowser): stock Playwright has `navigator.plugins.length === 0` and no `window.chrome` object). New headless mode made rendering-fingerprint tells largely vanish, so "real headful Chrome" is the bar and CDP-level signals rose in relative value ([crawlex CDP-vector](https://blog.crawlex.net/blog/cdp-detection-vector)).

### 1.3 JS-injection and context-stealth artifacts

- **Init-script / binding leaks.** Playwright's `addInitScript`/`addScriptToEvaluateOnNewDocument` and `exposeFunction` leave durable, page-visible traces: `page.exposeFunction` installs a `window.<fnName>` property (`exposeFunctionLeak` in [rebrowser-bot-detector](https://raw.githubusercontent.com/rebrowser/rebrowser-bot-detector/main/index.js)); Patchright itself documents its injected init scripts as detectable by **timing attacks** ([Patchright README, "Leaks"](https://github.com/Kaliiiiiiiiii-Vinyzu/patchright)).
- **Injected-code identity markers.** Playwright evaluates code with source markers naming the library, observable in error stacks (`sourceUrlLeak` detection; [crawlex: "the stack-trace marker is a property of how a specific automation library names its own injected code"](https://blog.crawlex.net/blog/cdp-detection-vector)). **[inference from the same mechanism]:** this is the same class as Selenium's historic `cdc_` properties in the DOM and `document.$cdc_asdjflasutopfhvcZLmcfl_` markers — vendor-specific identifier leaks of *injected* code, as opposed to driver-level CDP leaks.
- **`toString`-native wobbles from JS stealth.** JS-injection stealth (playwright-stealth/puppeteer-extra-stealth) overwrites built-ins and produces detectable side effects: DataDome detects "signatures or 'side effects' caused by how puppeteer-extra-plugin-stealth overrides some built-in properties", flags ~40M requests/week tied to that plugin ([DataDome stealth-plugin detection](https://datadome.co/threat-research/detecting-headless-chrome-puppeteer-extra-plugin-stealth)), and `Function.prototype.toString` re-wrapping is a well-known tell for CreepJS-style "prototype lie" checks ([CreepJS](https://github.com/abrahamjuliot/creepjs)).
- **Non-CDP input events** (`page.dispatch_event`/JS-`dispatchEvent`) produce `isTrusted=false` events; real user-identical input must go through the browser's native input pipeline (CDP `Input.*` or OS-level injection). **[inference — general Chromium behavior]**: CDP-synthesized input *is* trusted, but see §1.4 for why that is no longer enough.

### 1.4 The 2025-era finding that re-sunk all CDP drivers: cross-frame click geometry

Cloudflare rolled out (Feb 2025) a check that detects CDP clicks through a **Chrome bug, not lib-level fingerprints**: clicking inside a cross-origin iframe via CDP yields `MouseEvent.screenX/screenY` **relative to the iframe** (single digits) instead of relative to the main viewport (hundreds) as with real OS-level input. "We did some tests with the most popular frameworks — puppeteer, playwright, **patchright**, selenium, nodriver, and, as expected, all of them got detected" ([webscraper.io blog, Oct 24, 2025, "Google patches 100% precise Cloudflare Turnstile bot check"](https://webscraper.io/blog/google-patches-100-precise-cloudflare-turnstile-bot-check)). The Chrome fix (2023-era bug, Chromium issue filed/converged by a Google employee in Sept 2025) "hasn't been merged yet" at writing time, so this held into 2026.

### 1.5 Engine/network tells outside the driver

- **TLS/HTTP2 fingerprint**: a Chromium *binary* matches Chrome's JA3/JA4 only if it is Chrome-family built the same way; stock bundled Chromium deviates (the CloakBrowser table lists "TLS fingerprint: mismatch vs identical to Chrome").
- **WebGL renderer strings**: headless/instanced Chromium reports `Google SwiftShader` or no GPU; `getParameter(gl.RENDERER)` is a direct check used in modern detection suites ([palimpsest #3](https://github.com/copyleftdev/palimpsest/issues/3)). Absence or failure of WebGL breaks Turnstile clients (see §5.3).
- **mac/OS hardware pass-through**: font enumeration (emoji/CJK rendering hashes), audio, fonts — stock Linux containers hash badly in Kasada/Akamai emoji-canvas checks (documented in CloakBrowser's font-setup rationale, [README](https://github.com/CloakHQ/cloakbrowser)).

## 2. What Patchright specifically changes

Documented ([README](https://github.com/Kaliiiiiiiiii-Vinyzu/patchright) and [PyPI notes](https://pypi.org/project/patchright)):

1. **Runtime.enable bypassed by construction** — "the biggest Patch Patchright uses. To avoid detection by this leak, patchright avoids using Runtime.enable by executing Javascript in (isolated) ExecutionContexts." The driver manages its own isolated worlds (which also sidesteps the §1.1 probes entirely, since no Runtime domain is enabled at all), and `evaluate`/locators are rewired to obtain isolated contexts manually. Since Patchright 1.57 you can toggle main vs isolated worlds: `Locator.evaluate_all(..., isolated_context=False/True)` ([PyPI 1.57 changelog](https://pypi.org/project/patchright/)). **Cost (documented)**: in the default isolated mode, page main-world objects are not directly accessible from evaluations — hence the pending upstream TODO "Implement Option to choose Execution Context (Main/Isolated)" and the added parameter.
2. **`Console.enable` leak: full Console-API elimination** — console APIs do not work in Patchright; use JS loggers (also detectable) if needed (README). **[inference]**: this eliminates the whole class of console-preview serialization probes from our side; Proxy-prototype probes respond only to the site's own calls.
3. **Command-flag scrubbing**: `--disable-blink-features=AutomationControlled` added; `--enable-automation`, `--disable-popup-blocking`, `--disable-component-update`, `--disable-default-apps`, `--disable-extensions` removed — anti-`navigator.webdriver`, anti-"stealth-driver", restoring default apps/extensions (README).
4. **General Playwright leak scrubbing** — "poor setups and obvious detection points"; plus **closed shadow root interaction and XPath inside closed shadow roots** (README).
5. **Init scripts without Runtime.enable — via Playwright routes (HTML injection)**, self-removing `<script>` tags. Documented caveats: route-level edge-case bugs, and init scripts are theoretically detectable via timing (README, "Init Script Shenanigans" / "Leaks").
6. **Recommended "undetectable setup"** ([patchright-python README/PyPI](https://github.com/Kaliiiiiiiiii-Vinyzu/patchright-python)): real Google Chrome (`channel='chrome'`), headed, persistent context, `no_viewport=True`, no custom UA/headers. WebRTC leaks the real IP unless `--webrtc-ip-handling-policy=disable_non_proxied_udp` is set ([patchright-python#47](https://github.com/Kaliiiiiiiiii-Vinyzu/patchright-python/issues/47)).
7. **Brotector-clean only with CDP-Patches** — the README's own stealth claim is qualified: "Brotector ✅ (with [CDP-Patches](https://github.com/Kaliiiiiiiiii-Vinyzu/CDP-Patches/))" — i.e. residual debugger-domain artifacts only die with a further CDP-side patch layer.

**Inferred mechanics of the isolated-context approach.** By never enabling the Runtime domain, the entire triggering mechanism in §1.1 (inspector-serialization on `console.*`) is absent — carried further than rebrowser-patches, whose runtime-fix modes still re-enable Runtime briefly and thus keep a small race window at page-load ([rebrowser README](https://github.com/rebrowser/rebrowser-patches)). **[inference]**: Patchright is still Playwright — it uses CDP for navigation, input, network — so any vector its inheritance tree doesn't touch passes through unchanged (e.g. §1.4's Chrome-bug iframe click geometry); its own [Issue #30](https://github.com/Kaliiiiiiiiii-Vinyzu/patchright/issues/30) documents which Playwright tests it deliberately does not pass.

**[inference — limits]**: Patchright gives **runtime-level stealth inside a stock engine**. It cannot: make a bundled-Chromium TLS/HTTP2 signature Chrome-identical (compare §3); fix WebGL absence in headless (§5.3); repair the §1.4 Chrome cross-frame click bug until Google ships it; or hide a stealth-plugin-style JS patch if one is added (`toString` lies are detectable — §1.3).

## 3. Runtime-level patches vs. source-level (binary) stealth — complement, not substitute

### 3.1 The two families

- **Runtime-level (Patchright, rebrowser-patches, nodriver-style raw-CDP, Selenium-Driverless)**: sanitizes the *driver* — no `Runtime.enable`, no `--enable-automation`, no init-script strings — while leaving the browser binary untouched. Its weakness is everything Chromium-the-engine itself reports (TLS, WebGL, fonts, GPU, screen/headless geometry, §1.4 click geometry, plugin list).
- **Source-level (CloakBrowser — "not a patched config. Not a JS injection. A real Chromium binary with fingerprints modified at the C++ source level"** [CloakBrowser README](https://raw.githubusercontent.com/CloakHQ/cloakbrowser/main/README.md)**)**: masks the *engine's output surface* at compile time — canvas, WebGL, audio, fonts, GPU, screen, WebRTC, hardware reporting, `navigator.webdriver`, "CDP input behavior mimicking". 87 patches on Chromium 155 in Pro builds; per-profile seeds give coherent identities; TLS matches real Chrome (ja3n/ja4/Akamai per their test table); `window === worker` byte-identical ([cloakbrowse.com](https://cloakbrowse.com/en/)). Self-reported vs stock Playwright: reCAPTCHA v3 0.1→0.9, Turnstile FAIL→PASS (non-interactive and managed), `navigator.plugins` 0→5, `window.chrome` defined, `HeadlessChrome` UA→real UA, "CDP detection: Detected→Not detected" ([Test Results](https://github.com/CloakHQ/cloakbrowser)).

### 3.2 Where each wins and loses

- **Reference data point**: DataDome/rebrowser note that a hand-built Chromium *can* fix Runtime.consoleAPICalled at source, but "you will have a custom-built Chromium which is quite different from a typical Chrome which leads to many unique fingerprinting metrics" ([Rebrowser blog](https://rebrowser.net/blog/how-to-fix-runtime-enable-cdp-detection-of-puppeteer-playwright-and-other-automation-libraries)) — runtime-level patching gets a real-Chrome fingerprint trivially; source-level patching must continuously rebase its patch set (CloakBrowser rebases 87 patches onto every fresh Chromium milestone).
- **JS-injection detection: source-level wins.** JS-patched canvas/WebGL/audio produce detectable "prototype lies" for CreepJS/FingerprintJS (`Function.prototype.toString` re-wrapping, getters, timing anomalies — §1.3); a C++ recompile yields *genuine* implementations with no shim to detect. CloakBrowser states this explicitly ("Config-level patches break… Every Chrome update breaks them. Antibot systems detect the patches themselves") — the same reason playwright-stealth/undetected-chromedriver/config-patch tools age badly ([CloakBrowser README](https://raw.githubusercontent.com/CloakHQ/cloakbrowser/main/README.md)).
- **WebGL presence and Turnstile: source-level wins.** WebGL can only be made present-and-real from inside the engine; Camoufox's WebGL handling is one reason PixelScan-type checkers flag it (Botright README notes a PixelScan fail "Maybe caused by WebGL-disabling" — [Botright README](https://github.com/Vinyzu/Botright/blob/main/README.md); [CloakBrowser FAQ](https://cloakbrowser.dev/) describes Camoufox as "unstable beta" in early 2026).
- **Driver-level seams: runtime-level wins.** Even a perfect stealth binary still needs a driver, and an unpatched Playwright/Puppeteer driver reintroduces §1.1 leaks. CloakBrowser's own README recommends Playwright over Puppeteer because "Puppeteer's CDP protocol leaks automation signals that reCAPTCHA Enterprise can detect" — i.e. engine- and driver-level stealth are independent axes.

### 3.3 Our hybrid stack **[internal]**

Production stack: **CloakBrowser (source-level engine) primary lane; Patchright driving a separate Chromium/Chrome — the "obscura" CDP lane — as fallback.** Primary lane covers §1's engine-level vectors natively (TLS/JA4, real WebGL, plugins, fonts, hardware). Fallback lane covers residual *driver-artifact* vectors (Runtime.enable, Console, launch flags, exposed bindings), so failing over to a stock Chrome binary (crash recovery, relaunch from a persistent profile) never regresses into the leaks Patchright eliminates. The asymmetry: Patchright-for-CloakBrowser loses WebGL/TLS/geometry (§5.3); CloakBrowser-with-unpatched-driver loses Runtime/Console cleanliness. The strongest configuration is a source-level binary driven by a patched driver — structurally what Patchright already is (driver separated from binary).

## 4. CDP-over-custom-engine specifics (connectOverCDP, cross-frame targeting)

When our fallback lane connects to an *external* engine's CDP (`connect_over_cdp`) instead of launching its own browser, we inherit a documented set of Playwright-vs-CDP mismatch behaviors:

1. **Contexts/settings are not carried across.** "Playwright does not receive browser context options from an open browser, but operates only with those generated by playwright unilaterally" — new pages created over `connect_over_cdp` lose touch/hover/UA settings; Playwright's stance is "We assume control over the browser once connected" ([microsoft/playwright#9238](https://github.com/microsoft/playwright/issues/9238)). Driver flags (`hasTouch` etc.) then fail at runtime ([issue #9238 log excerpt](https://github.com/microsoft/playwright/issues/9238)).
2. **Creating new browser contexts is blocked by the engine**: `Target.createBrowserContext: Not allowed` over CDP for an engine that doesn't allow it ([microsoft/playwright#6715](https://github.com/microsoft/playwright/issues/6715)).
3. **Frame-targeting/remapping bugs**: "connectOverCDP replaces the page's main frame with a nested sandboxed iframe when its parentFrameId is unknown" ([microsoft/playwright#42955](https://github.com/microsoft/playwright/issues/42955)) — and the Camoufox maintainers describe the analogous gap as "Playwright can't click into OOPIFs", because nested cross-origin iframes span separate renderer processes/targets ([daijro/camoufox#549](https://github.com/daijro/camoufox/issues/549), referencing #150). Each OOPIF is its own CDP target; `Target.autoAttach` attaches them, but Playwright's client-side frame-tree model can drift from the process/target identity the engine reports.

**[internal]** We have observed in our obscura lane that cross-origin iframe evaluation over CDP can silently **misbind to the host (parent) frame's execution context**: the evaluation returns data whose `location`/`document` belongs to the top frame instead of the iframe, without a protocol error. This matches the bug class above (frame/target identity and context-isolation handling across OOPIF targets). **[inference]** Likely the driver resolves the frame's execution context through frame-id mapping while the engine auto-attaches child targets with different lifecycle timing, so `Runtime.evaluate({contextId})` goes out with a stale or default (main-frame) context id before the child target has produced its own execution-context event. Mitigation: after each navigation, wait for `Target.attachedToTarget`/`Runtime.executionContextCreated` for the specific OOPIF before evaluating; verify `document.location.href` inside the result before trusting it; prefer frame-scoped locator APIs over raw `evaluate` inside cross-origin iframes.

**[inference]** This is the underlying mechanism Turnstile's click check exploits (§1.4): both hinge on "where the CDP client thinks the input/context is" versus "where Chrome's own pipeline says it is" — one bug class, two failure modes (wrong *data* for us; wrong *event coordinates* for the anti-bot).

## 5. Practical guidance for an agent using Patchright as the fallback engine

### 5.1 Documented configuration floor (patchright-python README / PyPI)

- Chromium-family only; use `channel='chrome'` (real Google Chrome, not bundled Chromium), `headless=False`, `launch_persistent_context(user_data_dir=…)`, `no_viewport=True`, no custom UA or HTTP headers — the configuration the "undetectable" claim refers to.
- Add `--webrtc-ip-handling-policy=disable_non_proxied_udp` (see §2 item 6); match proxy geo to timezone/locale.
- Don't use console.log in a Patchright page (README); don't rely on `exposeFunction`-style bindings unless tested (`exposeFunctionLeak` in [rebrowser-bot-detector](https://raw.githubusercontent.com/rebrowser/rebrowser-bot-detector/main/index.js)).
- Route-based init scripts create edge cases in Playwright interception code ([README "Init Script Shenanigans"](https://github.com/Kaliiiiiiiiii-Vinyzu/patchright)).

### 5.2 Safe fallback actions ⇄ known-dead actions

| Action | Verdict | Basis |
|---|---|---|
| Load plain pages, evaluate in isolated context, gather fingerprint data (UA, languages, screen, window, canvas presence) | **Safe (documented stealth claims)** — passes Sannysoft, CreepJS, Pixelscan, IPHey, BrowserScan per README | Patchright leaves the JS-visible surface intact; its only documented leak surface is init-script timing, which current anti-bots don't check |
| Navigate Cloudflare/DataDome/Kasada/Akamai-protected pages | Mostly safe but **never free** — scoring continues on TLS, IP reputation, behavior; the inverse of "patches eliminate leaks" does not guarantee a pass ([rebrowser-patches README](https://github.com/rebrowser/rebrowser-patches)) | Patchright's `Cloudflare ✅` is "with the right setup": channel=chrome, headed, residential, clean IP |
| Interactive click inside cross-origin iframes | **[known-dead as of writing]** CDP clicks still leak iframe-relative screen coords (§1.4; Chromium fix pending) | webscraper.io Oct 2025; workaround = OS-level input (xdotool/pyautogui/robotjs) or engine-level humanized-input emulation |
| Solve Cloudflare Turnstile where WebGL is missing/absent | **[inference from documented engine limits]** Known-dead: Turnstile needs a real WebGL client; source-level builds show Turnstile FAIL→PASS while WebGL-disabled stacks flag PixelScan ([CloakBrowser table](https://github.com/CloakHQ/cloakbrowser); Botright README) | Patchright provides no WebGL fix — it never touches the engine |
| Bypass Cloudflare Bot Management broadly | Not achievable from the driver layer alone | "The bot detection decision happens at page load based on TLS fingerprint, JS fingerprint, and CDP detection — before any interaction is possible" ([omnideck #120](https://github.com/omnideck-dev/omnideck/issues/120)) |

### 5.3 Which lane should do which job

- **Fingerprint-reporting sanity pages / non-interactive probes** (Sannysoft/BrowserScan/Pixelscan/deviceandbrowserinfo/Incolumitas): safe in Patchright, ideally still in the fallback lane only — primary lane returns truth from a genuine source-level engine.
- **Plain Cloudflare navigation** (residential IPs, no forced Turnstile, low bot-score threshold): feasible on the fallback engine when there is no interactive Turnstile. Treat interactive Turnstile contact as a **[primary-lane capability]** (CloakBrowser binary + humanized input): WebGL and OS-geometry-real input both live at that layer, per the [CloakBrowser test results](https://github.com/CloakHQ/cloakbrowser).
- **Everything interactive** (Turnstile click, DataDome behavioral probes, reCAPTCHA Enterprise): delegate to humanize-capable lanes; Patchright alone does not humanize — input geometry still goes through the driver pipeline, and Turnstile's iframe-relative screenX/Y check defeats it. The fallback lane is for resilience, not as a primary substitute for the stealth engine **[internal]**.
